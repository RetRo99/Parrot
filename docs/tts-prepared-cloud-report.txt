store: cloud_books.id IS the client's library book id, a UUID the client chooses
(20261001000000_parrot_cloud_client_book_ids.sql:1-3, :32-33), so two devices hold the

Step 2: archive format; checks on unpack (list); what a rejected archive leaves
behind:
  A STORED zip, so the AAC is never recompressed and the payload is byte-identical
  through the round trip. manifest.json is ALWAYS FIRST, so an unpack knows what names
  and sizes it may accept before writing a byte; then one <64 hex key>.m4a per distinct
  key in manifest order, duplicates sharing one file. Name
  tts-prepared/<sha256(href)>/<sha256(settings)>.zip - hashes only.
  Checks on unpack: MANIFEST_NOT_FIRST, UNSUPPORTED_VERSION, IDENTITY_MISMATCH,
  CHAPTER_INCOMPLETE, UNSAFE_ENTRY, UNLISTED_ENTRY, DUPLICATE_ENTRY, MISSING_ENTRY,
  SIZE_MISMATCH, TOO_LARGE (checked WHILE READING, not only from the header), UNREADABLE.
  Escaping the target folder is impossible BY CONSTRUCTION, not by sanitising: the only
  accepted name is a 64-char lowercase hex key plus .m4a.
  What a rejected archive leaves behind: NOTHING. Everything goes into a staging folder
  beside the target and the target is touched only after every check passed.

Step 4: how a device learns what the cloud holds; download states built (list):
  How it learns: from the cloud_book_files rows it ALREADY syncs - Step 0 decided to keep
  prepared audio in the existing payload - read through cloudFilesFor(libraryBookId). A
  prepared chapter is a row with media type tts_prepared_audio and a relative path of
  tts-prepared/<sha256(href)>/<sha256(settings)>.zip, so a device finds a chapter's audio
  by hashing the href it already has and matching the PREFIX
  (TtsPreparedChapterArchive.chapterPathPrefix), and tells whether it was made for the
  settings now selected by comparing the WHOLE path. When the cloud holds more than one
  version, the one for the current settings wins.
  THE ONE PLACE THIS FALLS SHORT OF THE BRIEF: a device CANNOT read which OTHER voice or
  speed an archive was made for, because that part of the path is a hash and hashes do not
  run backwards. The brief asks for "which voice and speed". The alternative is putting a
  user-chosen voice id and rate in the path or in a new column, which means a second
  server change and puts text where the migration constrains the path to two hashes. So
  the row says "In Parrot Cloud, made for other settings - <size>" and names the exact
  settings only when they are the current ones; after the download the manifest is on
  disk and TtsPreparedStore.state reports OtherSettings(settings, ...) exactly as it
  already does for local audio, which is the only moment the user can act on it. A test
  asserts both halves of that.
  The engine again rather than beside it: enqueueAuxiliaryDownload(serverId,
  libraryBookId, mediaType, relativePath, destinationPath), defaulted on the interface,
  reuses the whole of processDownloadTransfer - resume from a partial staging file, the
  engine's own retry and backoff, and the cloud content hash check. One branch was added

  finalizeAuxiliaryDownload, which verifies the hash and moves the bytes to the path the
