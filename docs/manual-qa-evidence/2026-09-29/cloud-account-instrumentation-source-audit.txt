## Existing telemetry and gap

- Existing route-only signal: `NavigationAnalyticsEvent.SyncAndBackupViewed`, `sync_and_backup_screen_viewed`, emitted only after Home navigation reports the route visible; matching `sync_and_backup_route` visible breadcrumb. This was previously exercised under case 429. Preserve it and do not duplicate it in CloudAccountScreen/ViewModel.
- `CloudAccountViewModel` has no Analytics dependency and no `logEvent`, `logBreadcrumb` or `logException` call. The Cloud Account UI Gradle module has no Analytics API dependency and no common UI tests.
- Caught exceptions in auth/session restore, account linking, storage usage, sign-out, deletion, Sync Now and auto-backup persistence become UI state without operation outcomes or correlated diagnostics. `CancellationException` is rethrown without a bounded user-operation cancellation outcome. This is a deterministic source gap, not a device-observed behavior.
- No typed Cloud Account feature event model was found. New events must not include email, password, token, cloud-user/local-profile/server IDs, URLs, free-form error messages or raw exception messages. Expected bad credentials, form validation, ordinary OAuth cancellation and offline sync are not Crashlytics issues. Unexpected user-impacting failures should be reported once at the UI boundary without duplicate repository reports.
- Cases 370–371 remain deferred under the no cross-app/cross-device sync verification scope; no sync behavior will be asserted by this audit.

**Disposition:** confirmed instrumentation defect QA-BUG-0082; no fix or runtime result is claimed. Focused Cloud Account instrumentation and Samsung retests are pending.

## Separate suspected state issue — QA-BUG-0083

`CloudAccountViewModel.signOutAfterLinkConflict()` catches and ignores a non-cancellation exception from `signOutCloudAccountUseCase()`, then writes UI auth state `SignedOut`. The cloud repository's `signOut()` has a `finally` block that clears/replaces the current profile session, so source evidence alone cannot establish whether an actual stale authenticated session can remain. No cloud-account conflict or local sign-out failure was injected. This is separately registered as SUSPECTED, not a confirmed device bug; verify the cleanup invariant with a safe host fault-injection test before changing behavior.
