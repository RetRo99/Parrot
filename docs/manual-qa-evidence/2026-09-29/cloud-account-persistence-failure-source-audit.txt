## Reproduction path

1. Email sign-in or registration returns a `CloudAccount`; `SupabaseCloudAccountDataRepository` has already established/published its local Supabase session.
2. `SignInCloudAccountUseCase` or `RegisterCloudAccountUseCase` next calls `PendingCloudAuthenticationRepository.save()` as required local completion state.
3. If that local preference/database write throws, the use case propagates it. Before the fix there is no compensating repository sign-out or pending-record clear in either catch path.
4. The ViewModel catches the error and shows generic error state; while its `isLoading` flag was true, the auth observer could first update `authState=SignedIn`. `showError` then sets `showLinkConfirmation` when signed in with no `profileLink`. `LinkCloudAccountUseCase` requires the pending-auth record and rejects if it is absent.

This establishes a deterministic source path. A host fault-injection test must verify that the session is rolled back and the pending record cleared. No physical-device reproduction is claimed; safe Samsung injection needs an authorized disposable cloud account plus a local persistence fault fixture.

## Safety boundary

Never retain or emit email, password, OAuth code/token, account/profile ID, raw exception text or server URL. Expected auth rejection and user cancellation remain ordinary outcomes, not Crashlytics exceptions. The rollback itself must rethrow `CancellationException` and must not silently claim successful auth completion.
