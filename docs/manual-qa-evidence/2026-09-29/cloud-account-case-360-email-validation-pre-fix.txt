The email field remained neutral (no red/error styling and no field-specific supporting text); the generic form helper described email/password/terms, and the Create account button was disabled. [Screenshot: malformed field with generic helper](cloud-account-email-invalid-helper.png); [same malformed value with keyboard visible](cloud-account-email-invalid-signed-out.png).
3. Switched to Sign in and entered another malformed value (`qa@`). The field still showed no inline error; the software keyboard was visible. [Screenshot: malformed `qa@` field](cloud-account-email-invalid-qa-at.png). An additional sign-in screenshot shows the disabled submit and generic helper while the synthetic password remains masked: [sign-in state](cloud-account-email-invalid-signin.png).
4. Replaced it with `qa@example.com` solely to exercise syntactically valid formatting. No account operation was submitted and no password remained. [Screenshot: valid-format value, keyboard visible](cloud-account-email-valid-syntax.png).
5. Cleared the email field. The final UI tree showed empty email and password fields, the Parrot MainActivity remained foreground, and the Default profile/server fixture was unchanged. [Intermediate focused form before final clear](cloud-account-email-invalid-form-live.png).

- **Expected:** Inline, accessible email-format error appears for malformed non-empty input before any submit; correction removes the error and validation state recovers.
- **Actual:** No email-specific error text or error styling appeared for either malformed value. The existing helper is generic form guidance, not an email error. A syntactically valid value had no explicit feedback.
- **Functional result:** FAIL for case 360. No form submit, OAuth, network auth request or server mutation occurred.
- **Analytics:** Local logcat contained route/session restore output, but no validation-result event on invalid input or correction. Firebase Analytics ingestion is waived; no Firebase delivery is claimed.
- **Diagnostics:** No bounded validation failure/recovery breadcrumb appeared. This was ordinary input validation, so no Crashlytics non-fatal was expected.
- **Unexpected test-control detour:** One attempted field replacement while keyboard focus was absent did not edit the input; a subsequent Back returned to App Settings. The app responded to Back normally. The Bitwarden save prompt was declined; the following App Settings screenshot is [here](cloud-account-email-autofill-dismissed.png). Neither event is an app defect. Re-entered the screen and completed the validation observation using a focused email field.
- **Defect:** QA-BUG-0088, confirmed and recorded before code changes. The result ledger and bug register preserve the failure; a coupled inline-feedback and bounded validation-outcome fix is pending.

All recorded input examples are synthetic and locally cleared. DebugAnalyticsManager is local-only; Firebase Analytics ingestion is waived and Crashlytics delivery is not established. No cross-app or cross-device sync was tested.
