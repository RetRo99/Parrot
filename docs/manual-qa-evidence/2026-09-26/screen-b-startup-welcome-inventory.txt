Login instrumentation/failure map from source audit
- Existing `login_attempted`, `login_succeeded`, `login_failed` events exist; `login_attempted` currently supplies only `server_url_hash`, which is intentionally removed by the provider allowlist. Outcomes omit bounded server type/auth method/retry/cancel dimensions; no Login screen exposure event or Login operation breadcrumbs are emitted. This is QA-BUG-0012 and overlaps repository-wide QA-BUG-0006; Firebase Analytics delivery is waived, local-provider behavior remains the app-side check.
- Repository `onFailure` logs exceptions and LoginViewModel also calls `error.log`; for errors whose `shouldReportException` is true, one failed operation can produce two non-fatals. Repository logging is unconditional for expected network/auth outcomes. See QA-BUG-0004.
- After authenticator success, `LoginDataRepository` calls `ServerRegistry.addServer` and `saveCredentials` inside a plain `flatMap` transform. A thrown persistence exception escapes; LoginViewModel's `viewModelScope.launch` has no catch/finally around the operation, so loading may remain active and the exception may reach the uncaught coroutine handler. New case 753 and QA-BUG-0013 cover this failure path.
- Login success currently sets Firebase user identity to username/server-URL hashes (QA-BUG-0003); fix/verification is required before entering the demo credentials.
- Source does not yet guard repeated sign-in/OAuth intents while `isLoading`; rapid submit race remains a suspected case-526 risk pending focused test (QA-BUG-0014).

States and exits
- Loading: Splash is the startup loading route; case 471. Welcome has no loading indicator.
- Content: Welcome title/subtitle, feature cards, Get Started and Browse without account; case 1.
- Error/fallback: startup auth check exception falls back to Welcome; failure injection not yet verified on Samsung.
- Exit/navigation: Get Started → Login; guest choice → Home; Back behavior depends on root/navigation path; Home/background/resume/rotation/process restoration cases 9–14, 515–524.
- No test has been run for Welcome rotation, lifecycle, repeated taps, or system Back yet.

Current event/diagnostic dictionary
- `app_launch_route_resolved`: root auth route, `screen`, `source_screen=splash`, `entry_point=app_launch`, `outcome` success/fallback; emitted after auth-state resolution, not recomposition.
- `welcome_screen_viewed`: emitted from `LaunchedEffect` when Welcome becomes the visible nested destination; bounded screen/source/entry parameters.
- `welcome_action_attempted`: action values `get_started` or `browse_without_account`, outcome started.
- `welcome_action_completed`: same bounded actions, emitted when Login becomes visible or the guest preference is committed; terminal outcome succeeded.
- Diagnostic breadcrumbs cover auth-check start, route selection, Welcome visibility, Welcome action start, and guest preference persistence. No user text, credentials, URLs, book title or file path is sent.
- Debug provider logs are local-only; Firebase Analytics ingestion is waived and is not claimed. Crashlytics delivery remains unverified.
