Login instrumentation/failure map (source changes committed; Samsung action pass pending)
- `login_screen_viewed`: emitted once per actual visible Login destination with bounded source/entry-point fields. `LoginNavigation` keys the callback to the top destination, not general recomposition.
- `login_attempted`: accepted credentials/OAuth attempt; parameters are screen, action, server type, auth method, retry Boolean and `outcome=started`. No URL, username, password, token or correlation ID is in Analytics parameters.
- `login_succeeded`: emitted only after authentication and local credential persistence both succeed; includes server type, method, `outcome=succeeded` and elapsed milliseconds.
- `login_failed`, `login_cancelled` and `login_abandoned`: distinct terminal outcomes. Explicit OAuth cancellation has a typed cancellation flag; leaving during an active operation records abandonment. `oauth_login_step_failed` remains a bounded OAuth-stage event.
- Operation breadcrumbs carry screen/action/operation/stage/outcome, server type and a diagnostic-only correlation ID at start and terminal outcome. Unexpected failures are reported once at the Login recovery boundary. Expected credential rejection and connectivity/cancellation outcomes are not Crashlytics non-fatals. This is QA-BUG-0012; Analytics observation remains local-only under the user's waiver.
- QA-BUG-0004 lower-layer exception reporters were removed; expected HTTP/transport outcomes are classified, with UI as the single unexpected-failure report boundary. Unit/build checks pass; Samsung failure-path counts and Crashlytics delivery are not yet verified.
- QA-BUG-0013 is fixed in source to roll back in-memory registry/credential changes, compensate server registration, preserve cancellation and return a recoverable Login failure. A safe device write-fault fixture is unavailable, so new case 753 is BLOCKED for functional/runtime verification.
- QA-BUG-0003's account/URL-derived Firebase identity was removed; the committed cold-start verification confirms provider identity clears on startup. A successful Login identity-clear check is still pending.
- QA-BUG-0014's credentials/OAuth submission gate is committed and has a regression test. Samsung rapid-submit/delayed-network retest under case 526 remains pending; the prior source-audit risk is not closed by source inspection alone.

Current event/diagnostic dictionary
- `app_launch_route_resolved`: root auth route, `screen`, `source_screen=splash`, `entry_point=app_launch`, `outcome` success/fallback; emitted after auth-state resolution, not recomposition.
- `welcome_screen_viewed`: emitted from `LaunchedEffect` when Welcome becomes the visible nested destination; bounded screen/source/entry parameters.
- `welcome_action_attempted`: action values `get_started` or `browse_without_account`, outcome started.
- `welcome_action_completed`: same bounded actions, emitted when Login becomes visible or the guest preference is committed; terminal outcome succeeded.
- Diagnostic breadcrumbs cover auth-check start, route selection, Welcome visibility, Welcome action start, and guest preference persistence. No user text, credentials, URLs, book title or file path is sent.
- Debug provider logs are local-only; Firebase Analytics ingestion is waived and is not claimed. Crashlytics delivery remains unverified.
