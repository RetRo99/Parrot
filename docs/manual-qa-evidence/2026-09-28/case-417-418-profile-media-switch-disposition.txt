## 2026-09-29 retrospective feasibility correction

The case-417 BLOCKED disposition above describes the 2026-09-28 setup only: the disposable profile then had no audio-capable book/current playback, and no server ReadAloud fixture was used. It must not be interpreted as requiring authenticated server audio or as showing that EPUB playback cannot be tested.

The on-device TTS path is a valid local-media alternative. `ReaderViewModel.initTts()` checks for readable publication content, exposes available voices, selects the saved/system voice, and enables sentence playback when TTS is enabled; it is not gated on audiobook/server authentication. `ReaderScreen` exposes the TTS Play/Pause control when readable content is available and TTS is enabled. On 2026-09-29, a separate Samsung run on a retained local EPUB emitted a bounded `tts_playback_operation` attempt/success pair with `media_type=ebook`; the player showed Pause and EPUB progress advanced. Notification permission denial cancelled that TTS start ordinarily; the successful active-playback sample followed a temporary permission grant, which was restored to its captured denied baseline. See [Samsung local-TTS evidence](../2026-09-29/tts-samsung-normal-path.txt). This proves local EPUB TTS can reach actual playback on the Samsung, but it does not prove the EPUB was imported into the disposable profile or that playback survives a profile switch.

Source also presents a feasible route to the switch: the Reader hides Home bottom navigation; Home renders the mini-player outside Reader when now-playing information exists, while App Settings exposes profile selection. Reader close does not explicitly call TTS stop in the inspected path, but continued PLAYING after leaving Reader and through a profile switch is **unverified** and must be observed, not inferred. If it stops before the switch route is reachable, record the exact transition/state as the case result and assess whether a supported reachable path remains.
